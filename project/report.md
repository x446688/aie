**Краткое описание:**  
Проект решает задачу краткосрочного прогнозирования нагрузки на энергосистему Бразилии с использованием почасовых данных за 23 года (2000–2023). Высокая частота дискретизации (1 час) позволяет моделировать суточные, недельные и годовые паттерны потребления, что критически важно для балансировки сети и планирования генерации. Реализованы и сравнены четыре подхода: наивный базлайн, линейная регрессия (Ridge), LSTM и GRU; финальная модель развёрнута как REST API через FastAPI с поддержкой конфигурации, логирования и визуализации результатов.

## 2. Постановка задачи и контекст

### 2.1. Предметная область и задача
- **Задача:** Регрессия временного ряда — предсказание потребления электроэнергии (в МВт) на следующий час.
- **Пользователь:** Оператор энергосистемы, аналитик спроса, система автоматического планирования генерации.
- **Сценарий:** Загрузка исторических данных → получение прогноза → интеграция в систему диспетчеризации.

### 2.2. Формулировка в терминах ML
- **Вход:** Временной ряд с двумя колонками: `date` (datetime) и `value` (float, потребление в МВт).
- **Выход:** Скалярное значение — прогноз потребления на следующий временной шаг.
- **Ограничения:** 
  - Прогноз должен быть получен <100 мс (онлайн-инференс);
  - Модель должна работать с данными любого масштаба (автоопределение колонок);
  - Воспроизводимость результатов (фиксированный seed).

### 2.3. Целевые метрики
| Метрика | Почему выбрана |
|---------|---------------|
| **RMSE** | Штрафует крупные ошибки, важно для энергосистемы (перепроизводство/недопроизводство дорого) |
| **MAE** | Интерпретируемая ошибка в исходных единицах (МВт) |
| **MAPE** | Относительная ошибка, удобна для сравнения на разных масштабах данных |

## 3. Данные

### 3.1. Источник
- **Датасет:** [23 Years of Hourly Electric Energy Demand – Brazil](https://www.kaggle.com/datasets/arusouza/23-years-of-hourly-eletric-energy-demand-brazil) (Kaggle, открытый).
- **Период:** Январь 2000 — Январь 2023 (~200 000 записей).
- **Частота:** Почасовая.

### 3.2. Структура
```csv
index, hourly_demand
2000-01-01 00:00:00, 34673.9
2000-01-01 01:00:00, 33503.0
...
```
- `index`: временная метка (час);
- `hourly_demand`: целевая переменная, потребление в МВт (диапазон: 0–90 000).

### 3.3. Предобработка и EDA
**Основные шаги** (реализованы в `src/project/core.py::clean_timeseries()`):
1. Автоопределение колонок даты и значения (поддержка разных названий);
2. Приведение `date` к `datetime64`, `value` к `float`;
3. Сортировка по времени, удаление дубликатов;
4. Масштабирование `StandardScaler` (fit на train, transform на val/test).

**Наблюдения из EDA** (`notebooks/01_eda.ipynb`):
- Явная суточная сезонность (пики утром/вечером);
- Недельный паттерн (снижение нагрузки в выходные);
- Годовая сезонность (лето/зима, гидрологический цикл Бразилии);
- Отсутствие пропусков в исходных данных.

## 4. Модели и подходы

### 4.1. Базовые модели (baseline)
| Модель | Описание | RMSE (test) | Комментарий |
|--------|----------|-------------|-------------|
| **Naive** | Предсказывает последнее известное значение | ~7.66 | Минимальный базлайн, не учитывает паттерны |
| **Ridge** | Линейная регрессия с лагами [1,7,14,21,28] ч | ~3.67 | Учитывает линейные зависимости, быстрый инференс |

### 4.2. Улучшенные модели
| Модель | Архитектура | Гиперпараметры | RMSE (test) |
|--------|-------------|----------------|-------------|
| **LSTM** | 2 слоя, hidden=64, dropout=0.1 | lr=5e-4, epochs=50, batch=64 | ~10.76 |
| **GRU** | 2 слоя, hidden=64, dropout=0.1 | lr=5e-4, epochs=50, batch=64 | ~8.48 |

**Особенности обучения:**
- Early stopping по валідационной потере (patience=10);
- Scheduler `ReduceLROnPlateau` (factor=0.5);
- Фиксированный seed=42 для воспроизводимости.

### 4.3. Нейросетевые архитектуры
**LSTM/GRU** (`src/project/models.py`):
```
Input: (batch, window_size=28, 1)
   ↓
RNN Layer (LSTM/GRU): hidden=64, num_layers=2
   ↓
Last hidden state → Linear(64→1)
   ↓
Output: (batch, 1)
```
- Используется только последний hidden state (одношаговый прогноз);
- Dropout между слоями для регуляризации.

Эксперименты: `notebooks/02_baseline.ipynb`, `notebooks/03_models_tuning.ipynb`.

## 5. Экспериментальный протокол и результаты

### 5.1. Протокол
- **Разделение:** Temporal split (без перемешивания!):
  - Train: 70% (ранние данные)
  - Val: 15% (средние)
  - Test: 15% (поздние, не участвуют в обучении)
- **Метрики:** Считаются на тестовом наборе после инверсии скалирования (в исходных единицах МВт).

### 5.2. Сравнение моделей
| Модель | MAE (МВт) | RMSE (МВт) | MAPE (%) | Время инференса |
|--------|-----------|------------|----------|-----------------|
| Naive | 6.56 | 7.66 | 6.41 | <1 мс |
| Ridge | **2.76** | **3.67** | **2.70** | ~5 мс |
| LSTM | 8.59 | 10.76 | 8.01 | ~25 мс |
| GRU | 6.97 | 8.48 | 6.72 | ~20 мс |

### 5.3. Выбор финальной модели
**Выбрана: Ridge**  
**Причины:**
1. Наименьшая ошибка на тесте (RMSE=3.67 vs 7.66–10.76 у остальных);
2. Быстрый инференс (~5 мс) — подходит для онлайн-прогнозирования;
3. Интерпретируемость: веса лагов показывают важность разных временных сдвигов;
4. Устойчивость: не требует GPU, меньше гиперпараметров для тюнинга.

**Trade-offs:**
- LSTM/GRU теоретически лучше ловят нелинейные зависимости, но на данном датасете переобучаются (высокий val loss);
- Ridge проигрывает в гибкости, но выигрывает в надёжности и скорости.

## 6. Архитектура решения и сервис

### 6.1. Пайплайн
```
[CSV-файл] 
    ↓
clean_timeseries() → стандартизация колонок
    ↓
Scaler.transform() → масштабирование (загруженный scaler)
    ↓
make_windows() → формирование окна (last 28 часов)
    ↓
Model.forward() → прогноз в scaled space
    ↓
Scaler.inverse_transform() → возврат к МВт
    ↓
JSON-ответ с прогнозом
```

### 6.2. API Endpoints
| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/` | Веб-интерфейс для загрузки CSV |
| `POST` | `/predict` | Прогноз: принимает CSV, возвращает `{predicted_value, for_date, model, latency_ms}` |
| `GET` | `/health` | Health-check: `{status, model_available, version}` |
| `GET` | `/docs` | Swagger UI для интерактивного тестирования |

**Пример запроса:**
```bash
curl -X POST http://localhost:8000/predict \
  -F "file=@data/example.csv" | jq
```

**Ответ:**
```json
{
  "predicted_value": 82.34,
  "for_date": "2024-01-06T00:00:00",
  "model": "ridge",
  "latency_ms": 12.3,
  "input_rows": 1100
}
```

### 6.3. Технологический стек
- **Backend:** FastAPI, Pydantic, Uvicorn
- **ML:** PyTorch (LSTM/GRU), scikit-learn (Ridge, StandardScaler)
- **Данные:** pandas, numpy
- **Конфигурация:** PyYAML (`configs/default.yaml`)
- **Логирование:** стандартный `logging` + RotatingFileHandler
- **Развёртывание:** 
  ```bash
  uvicorn src.project.api:app --host 0.0.0.0 --port 8000
  ```
  (Docker-файл опционален, не включён в базовую поставку)

## 8. Ограничения и дальнейшая работа

### Текущие ограничения
1. **Одношаговый прогноз:** Модель предсказывает только следующий час; многошаговое прогнозирование (рекуррентное) не реализовано.
2. **Нет экзогенных признаков:** Используются только исторические значения спроса; погода, праздники, цена на энергию не учитываются.
3. **Привязка к масштабу данных:** Скалер обучается на конкретном датасете; для нового источника требуется переобучение.
4. **Нейросети переобучаются:** LSTM/GRU показывают худшие результаты на тесте, чем простая линейная модель — возможно, требуется больше данных или регуляризация.

### Что можно улучшить
- **Безопасность модели**: можно имплементировать методики базовой кибербезопасности ИИ
- **Многошаговое прогнозирование:** Рекуррентная генерация (predict → append → repeat) для прогноза на 24–168 часов вперёд;
- **Экзогенные признаки:** Добавление температуры, типа дня (рабочий/выходной), праздников через `exog_features`;
- **Онлайн-мониторинг:** Логирование предсказаний и фактических значений, расчёт скользящей метрики для детекции дрейфа;
- **Ансамбли:** Взвешенное усреднение прогнозов Ridge + GRU для повышения устойчивости;
- **Контейнеризация:** `Dockerfile` для воспроизводимого развёртывания в production.
