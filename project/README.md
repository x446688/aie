## 2. Структура проекта

Проект организован в следующей структуре:

- `pyproject.toml` – файл uv-проекта.
- `uv.lock` - lock-файл uv-проекта.
- `report.md` – отчёт по проекту (постановка задачи, данные, эксперименты, результаты).
- `self-checklist.md` – чеклист самопроверки проекта перед сдачей.
- `notebooks/` – экспериментальные ноутбуки:
  - EDA, прототипы моделей, отдельные эксперименты.
- `src/` – основной код проекта:
  - модули для работы с данными;
  - обучение моделей;
  - запуск сервиса/скриптов.
- `data/` – демонстрационные/учебные данные:
  - **только открытые, синтетические или обезличенные данные;**
  - при необходимости – небольшие выборки для быстрого запуска.
- `configs/` – конфигурационные файлы:
  - `.yaml`, `.json`, `.env.example` и т.п.
- `artifacts/` – сохранённые модели, отчёты, результаты экспериментов.
  - best_model.joblib - Финальная модель
  - metrics.json - Сравнение метрик
  - training_history.json - Кривые обучения (JSON)
  - scaler.joblib - Scaler отдельно
  - training_loss_curves.png - Train/val loss по эпохам
  - predictions_vs_actual.png - Факт vs прогноз для всех моделей
  - residuals_distribution.png - Гистограммы ошибок
  - model_comparison.png - Бар-чарт: сравнение по RMSE
- `tests/` - базовые юнит-тесты.

Опишите, как именно воспроизвести основные сценарии использования проекта.

Примеры (заполните под свой случай):

### 4.1. Запуск обучения модели

```bash
uv run service train-models data/example.csv --window-size 24 # обучение на синтетическом датасете с окном в 24 часа

```
После обучения в artifacts/ появятся:

### 4.2. Запуск сервиса (API/веб-интерфейс)

```bash
# Development-режим (с авто-релоадом)
uv run uvicorn src.project.api:app --host 0.0.0.0 --port 8000 --reload

# Production-режим
uv run uvicorn src.project.api:app --host 0.0.0.0 --port 8000
```

**Эндпоинты:**
| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/` | Простой веб-интерфейс для загрузки CSV |
| `POST` | `/predict` | Прогноз следующего значения по загруженному CSV |
| `GET` | `/health` | Health-check: проверка доступности модели |
| `GET` | `/docs` | Swagger UI для интерактивного тестирования API |

**Тестирование через curl:**
```bash
curl -X POST http://localhost:8000/predict \
  -F "file=@data/example.csv" | jq
```

Ожидаемый ответ:
```json

  "for_date": "2024-01-06T00:00:00",
  "model": "ridge",
  "latency_ms": 12.3,
  "input_rows": 1100

```

## 5. Данные

- **Источник:** [23 Years of Hourly Electric Energy Demand – Brazil](https://www.kaggle.com/datasets/arusouza/23-years-of-hourly-eletric-energy-demand-brazil) (Kaggle, открытый датасет).
- **Период:** 2000–2023, почасовая дискретизация (~200 000 записей).
- **Признаки:** 
  - `index` — временная метка (час);
  - `hourly_demand` — потребление электроэнергии в МВт (0–90 000).
- **Обоснование выбора:**  
  Почасовые данные позволяют моделировать многоуровневые временные зависимости: суточные пики (утро/вечер), недельные циклы (рабочие/выходные), сезонность (лето/зима, гидрологический цикл в Бразилии). Это делает датасет репрезентативным тестом для сравнения классических и глубоких моделей прогнозирования.
- **Хранение в репозитории:**  
  В `data/` лежит только небольшая подвыборка `example.csv` для быстрого запуска. Полный файл `energy_demand_hourly_brazil.csv` необходимо скачать отдельно и поместить в ту же папку.

## 8. Ограничения и дальнейшая работа

**Текущие ограничения:**
- Модель предсказывает только одно значение вперёд (next-hour forecast); многошаговое прогнозирование не реализовано.
- Не используются экзогенные признаки (температура, праздники, цена на энергию) — только история самого ряда.
- Scaler и модель привязаны к конкретному датасету; для нового источника требуется переобучение.

**Направления развития:**
- Добавить рекуррентное многошаговое прогнозирование (predict-next → append → repeat);
- Интегрировать внешние признаки через `exog_features` в `make_windows()`;
- Реализовать онлайн-мониторинг: логировать предсказания и фактические значения, считать скользящую метрику;
- Добавить поддержку нескольких датасетов через `dataset_name` в конфиге;
- Контейнеризация: `Dockerfile` для воспроизводимого деплоя.
- Проработать предотвращение атак на модель.
